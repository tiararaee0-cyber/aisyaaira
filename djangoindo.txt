### 2.4.1 Penyiapan Basis Data

Sekarang, buka `mysite/settings.py`. Ini adalah modul Python normal dengan variabel tingkat modul yang merepresentasikan pengaturan Django.

Secara bawaan, konfigurasi `DATABASES` menggunakan SQLite. Jika kamu baru mengenal basis data, atau hanya ingin mencoba Django, ini adalah pilihan termudah. SQLite sudah disertakan dalam Python, jadi kamu tidak perlu menginstal apa pun untuk menggunakannya.

Namun, saat kamu memulai proyek Django pertamamu yang sebenarnya, kamu mungkin ingin menggunakan basis data yang lebih andal dan dapat diskalakan seperti PostgreSQL. Django juga memiliki dukungan untuk pengalihan basis data (database switching) di masa depan.

Jika kamu ingin menggunakan basis data lain, baca dokumentasi tentang cara menyesuaikan dan mengonfigurasi basis datamu sendiri.



### **Dokumentasi Django, Rilis 5.2.8.dev202510180008**

Saat kamu mengedit `mysite/settings.py`, atur `TIME_ZONE` ke zona waktu kamu.

Juga, perhatikan pengaturan `INSTALLED_APPS` di bagian atas file tersebut. Ini mencantumkan nama semua aplikasi Django yang diaktifkan dalam instance Django kamu. Aplikasi ini dapat digunakan di beberapa proyek, dan kamu juga dapat membuat serta membagikannya kepada orang lain.

Secara bawaan, `INSTALLED_APPS` berisi aplikasi berikut, yang disertakan dengan Django:

* `django.contrib.admin` – Situs admin. Kamu akan menggunakannya sebentar lagi.
* `django.contrib.auth` – Sistem otentikasi.
* `django.contrib.contenttypes` – Kerangka kerja untuk tipe konten.
* `django.contrib.sessions` – Kerangka kerja sesi.
* `django.contrib.messages` – Kerangka kerja pesan.
* `django.contrib.staticfiles` – Kerangka kerja untuk mengelola file statis.

Aplikasi-aplikasi ini diaktifkan secara default sebagai kenyamanan untuk kasus umum.

Beberapa aplikasi di atas menggunakan setidaknya satu tabel database, jadi kita perlu membuat tabel-tabel ini di database sebelum dapat digunakan. Untuk melakukannya, jalankan perintah berikut:

```
python manage.py migrate
```

Perintah `migrate` akan memeriksa pengaturan `INSTALLED_APPS` dan membuat tabel database yang diperlukan sesuai dengan pengaturan database di `mysite/settings.py`. Ini juga akan menjalankan migrasi database bawaan untuk aplikasi yang disertakan (akan dijelaskan nanti). Kamu akan melihat pesan untuk setiap migrasi yang diterapkan.

Jika kamu tertarik, jalankan perintah seperti berikut untuk database kamu, misalnya:

* `\dt` (PostgreSQL)
* `SHOW TABLES;` (MariaDB, MySQL)
* `.tables` (SQLite)
* atau `SELECT TABLE_NAME FROM USER_TABLES;` (Oracle)

Perintah-perintah tersebut akan menampilkan tabel yang dibuat oleh Django.

#### **Untuk yang minimalis**

Seperti yang disebutkan, aplikasi bawaan disertakan untuk kasus umum, tetapi tidak semua orang membutuhkannya.
Jika kamu tidak ingin menggunakan semuanya, kamu dapat mengomentari atau menghapus baris yang sesuai dari `INSTALLED_APPS` sebelum menjalankan `migrate`.

### **2.4.2 Membuat Model**

Sekarang kita akan mendefinisikan model—secara sederhana, tata letak database kamu, dengan metadata tambahan.

#### **Filosofi**

Model adalah lapisan tunggal yang menggambarkan struktur informasi tentang data kamu.
Model ini berisi field penting dan perilaku data yang kamu simpan.
Django mengikuti *Prinsip DRY (Don't Repeat Yourself)*.
Tujuannya adalah untuk mendefinisikan data kamu hanya sekali.



### **Django Documentation, Release 5.2.8.dev202510180008**

Model ini berada di satu tempat dan secara otomatis menurunkan hal-hal lain darinya.

Ini juga mencakup migrasi — tidak seperti di Ruby On Rails, misalnya, migrasi di Django sepenuhnya diturunkan dari model kamu, dan pada dasarnya Django dapat menjalankan semuanya untuk memperbarui skema basis data agar sesuai dengan model kamu saat ini.

Untuk aplikasi polling kita, kita akan membuat dua model: **Question** dan **Choice**.
Sebuah **Question** memiliki teks pertanyaan dan tanggal publikasi.
Sebuah **Choice** memiliki dua field: teks pilihan dan jumlah suara.
Setiap **Choice** dikaitkan dengan sebuah **Question**.

Konsep-konsep ini direpresentasikan oleh kelas Python.
Edit file `polls/models.py`, sehingga terlihat seperti ini:

```python
from django.db import models

class Question(models.Model):
    question_text = models.CharField(max_length=200)
    pub_date = models.DateTimeField("date published")

class Choice(models.Model):
    question = models.ForeignKey(Question, on_delete=models.CASCADE)
    choice_text = models.CharField(max_length=200)
    votes = models.IntegerField(default=0)
```

Di sini, setiap model direpresentasikan oleh sebuah kelas yang mewarisi dari `django.db.models.Model`.
Setiap model memiliki sejumlah variabel kelas, yang masing-masing merepresentasikan sebuah field basis data dalam model.

Setiap field direpresentasikan oleh instance dari kelas **Field** – misalnya, `CharField` untuk field karakter dan `DateTimeField` untuk field tanggal/waktu.
Hal ini memberitahu Django jenis data yang dimiliki setiap field.

Nama setiap instance field (misalnya, `question_text` atau `pub_date`) adalah nama field dalam format ramah-mesin.
Kamu akan menggunakan nama ini di kode Python kamu, dan database akan menggunakannya sebagai nama kolom.

Kamu dapat memberikan argumen posisi opsional pertama ke **Field** untuk menentukan nama yang dapat dibaca manusia.
Itu digunakan di beberapa bagian terkomputerisasi dari Django, dan di dokumentasi admin.
Jika argumen ini tidak diberikan, Django akan menggunakan nama ramah-mesin sebagai gantinya.
Dalam contoh ini, kita hanya mendefinisikan nama yang dapat dibaca manusia untuk `Question.pub_date`.
Untuk semua field lain di model ini, nama ramah-mesin sudah cukup sebagai nama yang dapat dibaca manusia.

Beberapa kelas **Field** memiliki argumen yang diperlukan.
`CharField`, misalnya, mengharuskan kamu memberikan `max_length`.
Itu digunakan tidak hanya di database sendiri, tetapi juga dalam validasi nanti.

Sebuah **Field** juga dapat memiliki argumen opsional.
Dalam kasus ini, kita menetapkan nilai default `votes` ke 0.

### **Mengaktifkan Model**

Sekarang Django tahu bahwa ada dua model di aplikasi `polls`.
Namun, model ini belum dimasukkan ke dalam database kamu.
Untuk melakukannya, kita harus memberi tahu Django bahwa model-model tersebut adalah bagian dari aplikasi kita dan kemudian membuat migrasi yang akan menghasilkan tabel-tabelnya di database.

1. **Tambahkan aplikasi ke `INSTALLED_APPS`**

   Edit file `mysite/settings.py` dan tambahkan referensi ke konfigurasi aplikasi `polls` di pengaturan `INSTALLED_APPS` kamu.
   Itu akan terlihat seperti ini:

   ```python
   INSTALLED_APPS = [
       'polls.apps.PollsConfig',
       'django.contrib.admin',
       'django.contrib.auth',
       'django.contrib.contenttypes',
       'django.contrib.sessions',
       'django.contrib.messages',
       'django.contrib.staticfiles',
   ]
   ```

   Dengan menambahkan `'polls.apps.PollsConfig'`, kamu memberi tahu Django untuk menyertakan aplikasi `polls` saat proyek dijalankan.

2. **Buat migrasi untuk model baru**

   Jalankan perintah ini di terminal kamu:

   ```bash
   python manage.py makemigrations polls
   ```

   Django akan memberi tahu bahwa ia telah membuat file migrasi baru, sesuatu seperti:

   ```
   Migrations for 'polls':
     polls/migrations/0001_initial.py
       - Create model Question
       - Create model Choice
   ```

   File migrasi adalah skrip Python yang memberi tahu Django bagaimana membuat (atau mengubah) tabel di database untuk mencerminkan model kamu.

3. **Terapkan migrasi ke database**

   Setelah migrasi dibuat, jalankan perintah berikut untuk menerapkannya:

   ```bash
   python manage.py migrate
   ```

   Ini akan menjalankan migrasi yang belum diterapkan, membuat tabel-tabel baru di database sesuai model `Question` dan `Choice`.

---

### **Memeriksa Model yang Diterapkan**

Kamu dapat melihat SQL yang akan dijalankan Django tanpa benar-benar mengeksekusinya, dengan menggunakan perintah:

```bash
python manage.py sqlmigrate polls 0001
```

Perintah ini akan menampilkan pernyataan SQL mentah yang digunakan untuk membuat tabel-tabel di database, misalnya (bergantung pada backend database kamu):

```sql
CREATE TABLE "polls_question" (
    "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
    "question_text" varchar(200) NOT NULL,
    "pub_date" datetime NOT NULL
);
CREATE TABLE "polls_choice" (
    "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
    "question_id" integer NOT NULL REFERENCES "polls_question" ("id") DEFERRABLE INITIALLY DEFERRED,
    "choice_text" varchar(200) NOT NULL,
    "votes" integer NOT NULL
);
```

### Teks Terjemahan Halaman 31 (Django Documentation)

Dengan menjalankan perintah `makemigrations`, kamu memberi tahu Django bahwa kamu telah membuat beberapa perubahan pada model di proyekmu (dalam hal ini kamu membuat model baru) dan bahwa kamu ingin perubahan tersebut disimpan sebagai migrasi.

Migrasi adalah cara Django menyimpan perubahan pada model (dan karenanya pada skema database) — mereka adalah file di dalam direktori disk. Kamu bisa membaca migrasi untuk modelmu jika mau; misalnya, file ini `polls/migrations/0001_initial.py`. Jangan khawatir, kamu tidak diharapkan untuk membaca setiap kali Django membuatnya, tetapi file tersebut dirancang agar mudah dibaca oleh manusia jika kamu ingin memahami bagaimana Django melakukan perubahan.

Ada perintah yang akan menjalankan migrasi ini untukmu dan mengelola skema database secara otomatis — perintah ini disebut `migrate`, dan kita akan sampai ke sana sebentar lagi. Sekarang, mari kita lihat SQL apa yang akan dijalankan oleh migrasi tersebut.
Jalankan perintah berikut di terminalmu:

```
python manage.py sqlmigrate polls 0001
```

Kamu akan melihat sesuatu yang mirip dengan berikut ini (kami telah memformatnya agar lebih mudah dibaca):

```
BEGIN;
--
-- Membuat model Question
--
CREATE TABLE "polls_question" (
    "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "question_text" varchar(200) NOT NULL,
    "pub_date" timestamp with time zone NOT NULL
);

--
-- Membuat model Choice
--
CREATE TABLE "polls_choice" (
    "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "choice_text" varchar(200) NOT NULL,
    "votes" integer NOT NULL,
    "question_id" bigint NOT NULL
);
ALTER TABLE "polls_choice"
ADD CONSTRAINT "polls_choice_question_id_c5b4b260_fk_polls_question_id"
FOREIGN KEY ("question_id")
REFERENCES "polls_question" ("id")
DEFERRABLE INITIALLY DEFERRED;
```


```
CREATE INDEX "polls_choice_question_id_c5b4b260" ON "polls_choice" ("question_id");
COMMIT;
```

**Catatan berikut ini:**

* Hasil keluaran yang tepat akan berbeda tergantung pada basis data yang kamu gunakan. Contoh di atas dihasilkan untuk PostgreSQL.
* Nama tabel dibuat secara otomatis dengan menggabungkan nama aplikasi (`polls`) dan nama model dalam huruf kecil (`question` dan `choice`). (Kamu bisa mengubah perilaku ini.)
* Primary key (`id`) ditambahkan secara otomatis. (Kamu juga dapat menggantinya.)
* Secara konvensi, Django menambahkan `"_id"` ke nama field *foreign key*. (Ya, kamu juga bisa mengubah ini.)
* Hubungan *foreign key* ditampilkan secara eksplisit oleh *FOREIGN KEY constraint*. Jangan khawatir tentang bagian `DEFERRABLE`; ini hanya memberi tahu PostgreSQL untuk menunda pemeriksaan *foreign key* hingga akhir transaksi.
* Itu terkait dengan basis data yang kamu gunakan, misalnya tipe field khusus basis data seperti `auto_increment` (MySQL), `bigserial PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY` (PostgreSQL), atau *integer primary key autoincrement* (SQLite) ditambahkan secara otomatis oleh Django. Hal yang sama berlaku untuk pengutipan nama field—misalnya, menggunakan tanda kutip ganda atau tunggal.
* Perintah `sqlmigrate` sebenarnya **tidak menjalankan migrasi** pada basis data kamu — alih-alih, ia hanya menampilkannya di layar agar kamu dapat melihat SQL yang akan dijalankan Django. Ini berguna untuk memeriksa apa yang akan dilakukan Django, atau jika kamu memiliki administrator basis data yang perlu meninjau skrip SQL sebelum dijalankan.

Jika kamu tertarik, kamu juga dapat menjalankan perintah `python manage.py check`; ini memeriksa apakah ada masalah dalam proyekmu tanpa membuat migrasi atau menyentuh basis data.

Sekarang, jalankan perintah `migrate` untuk membuat tabel model di basis data kamu:

```
$ python manage.py migrate
```

Output-nya kira-kira seperti ini:

```
Operations to perform:
  Apply all migrations: admin, auth, contenttypes, polls, sessions
Running migrations:
  Rendering model states... DONE
  Applying polls.0001_initial... OK
```

Perintah `migrate` menjalankan semua migrasi yang belum diterapkan (Django melacak migrasi mana yang sudah diterapkan dengan membuat tabel khusus di basis data). Ia menjalankan migrasi-migrasi tersebut terhadap basis data kamu — pada dasarnya menyinkronkan perubahan yang telah kamu buat pada model dengan skema di basis data.

Migrasi sangat kuat dan memungkinkan kamu mengubah model seiring waktu, saat kamu mengembangkan proyek, tanpa perlu menghapus basis data atau tabel yang sudah ada. Django memiliki spesialisasi dalam memperbarui basis data langsung, dengan aman dan mudah.  



Tanpa kehilangan data. Kita akan membahasnya lebih dalam di bagian selanjutnya dari tutorial ini, tetapi untuk saat ini, ingat panduan tiga langkah untuk membuat perubahan pada model:

1. **Ubah model kamu** (`models.py`).
2. **Jalankan** `python manage.py makemigrations` **untuk membuat migrasi** dari perubahan tersebut.
3. **Jalankan** `python manage.py migrate` **untuk menerapkan perubahan tersebut ke basis data.**

Alasan mengapa ini adalah perintah yang terpisah adalah karena kamu akan meng-*commit* migrasi ke sistem kontrol versi bersama dengan aplikasi web kamu; hal ini tidak hanya membuat proses pengembangan lebih mudah, tetapi juga memungkinkan pengembang lain dan lingkungan produksi untuk mendapatkan struktur basis data yang sama.

Baca dokumentasi **django-admin** untuk informasi lengkap tentang apa yang dapat dilakukan oleh utilitas **manage.py**.

from django.db import models

class Question(models.Model):
    # ...
    def __str__(self):

class Choice(models.Model):

Penting untuk menambahkan metode `__str__()` ke model kamu — tidak hanya untuk kenyamanan saat menggunakan *interactive prompt*, tetapi juga karena representasi objek tersebut digunakan di seluruh antarmuka administratif Django yang dibuat secara otomatis.

```python
import datetime

from django.db import models
from django.utils import timezone

class Question(models.Model):
    # ...
    def was_published_recently(self):
        return self.pub_date >= timezone.now() - datetime.timedelta(days=1)
```

Perhatikan penambahan *import* untuk modul `datetime` dan `from django.utils import timezone`, untuk menggunakan waktu standar Python dan *utilities* zona waktu Django di `django.utils.timezone`, yang direkomendasikan untuk digunakan.

### **2.5 Membuat Tampilan Publik (Views)**

Sekarang setelah kita memiliki sistem admin untuk mengelola data, saatnya membuat *tampilan publik* untuk pengguna — yaitu halaman web tempat orang bisa melihat pertanyaan dan memberikan suara (*vote*).

Sebelumnya, kita sudah membuat tampilan sederhana di file `polls/views.py`, yang hanya mengembalikan teks sederhana dari fungsi `HttpResponse`. Sekarang kita akan membuat tampilan yang lebih kompleks dengan menggunakan *template*.

---

### **Langkah 1: Tambahkan URL untuk Tampilan Detail**

Buka file `polls/urls.py` dan ubah agar terlihat seperti berikut:

```python
from django.urls import path
from . import views

app_name = "polls"
urlpatterns = [
    path("", views.index, name="index"),
    path("<int:question_id>/", views.detail, name="detail"),
]
```

Di sini, kita menambahkan *path parameter* baru `question_id` yang akan mengarah ke tampilan detail setiap pertanyaan.

---

### **Langkah 2: Tambahkan Fungsi View Baru**

Selanjutnya, buka file `polls/views.py` dan tambahkan fungsi `detail` berikut:

```python
from django.http import HttpResponse
from .models import Question

def detail(request, question_id):
    return HttpResponse(f"You're looking at question {question_id}.")
```

Saat pengguna mengunjungi URL seperti `/polls/5/`, mereka akan melihat pesan:

> “You're looking at question 5.”

---

### **Langkah 3: Menampilkan Pertanyaan dari Database**

Sekarang ubah tampilan `detail` agar mengambil data *Question* dari database, bukan hanya menampilkan teks statis.

```python
from django.shortcuts import get_object_or_404, render
from .models import Question

def detail(request, question_id):
    question = get_object_or_404(Question, pk=question_id)
    return render(request, "polls/detail.html", {"question": question})
```

Fungsi `get_object_or_404()` akan menampilkan halaman kesalahan 404 jika pertanyaan tidak ditemukan.
